## Furniture Fact Extractor V1 (`hearth_fact_extractor.py`)

- **Purpose**: Turn organizational text Hearth is allowed to see into candidate durable facts ("Furniture") about a Building, for a human manager to approve or dismiss. Explicitly not a Watcher ("did something happen?") — it asks "did Hearth learn a durable fact?" Governed by "the because test" (:15-20): "if a statement only makes sense because of something else, it does not belong in Furniture" — conclusions like "is struggling" are rejected and belong to Soul/Worldview instead.
- **What it knows**: The 7-category Furniture taxonomy; a conservative confidence floor (`MIN_CONFIDENCE = 0.6`); a hard-coded go-live cutoff (`GO_LIVE_AT = "2026-07-11T00:00:00+00:00"`, :83) below which nothing is ever evaluated — no historical backfill in V1, and the module's own comment flags this constant needs manual adjustment if the real introduction date differs (worth a spot-check: this environment's "today" is 2026-07-12, one day after the constant); the 7 approved Pathway source tables plus check-in answers (8 `source_type`s total); deterministic candidate-generation rules; a two-step duplicate-suppression strategy (exact fingerprint, then a narrow Gemini semantic-equivalence check).
- **What it can read**: Connects to Pathway's own database **directly**, read-only (`mode=ro`), via `DATABASE_URL` — the same pattern as `hearth_soul.py`/`morning_briefing.py`. Reads exactly 8 source types, all mapped onto the Sensory Policy's Category A list: `creator_notes`, `shop_creator_notes` (kept as two source types because of an overlapping-id-sequence quirk between the underlying tables, not a design choice), `community_posts`, `community_comments`, `training_comments`, `support_messages`, `announcements`, and `checkin_answers` (fetched via a hand-rolled join, asymmetric to the declarative `SOURCE_CONFIGS` shape used by the other 7). Also reads `hearth_memory.db`: `hearth_entities` (candidate resolution), `hearth_entity_furniture` (dedup), `hearth_furniture_proposals`/`hearth_processed_sources` (dedup/ledger).
- **What it can write**: Exactly two tables in `hearth_memory.db`, both via `hearth_furniture_proposals.py`: `hearth_furniture_proposals` (one row per accepted candidate) and `hearth_processed_sources` (one row per evaluated source record, only when not a dry run). **Never** writes `hearth_entity_furniture`, `hearth_entities`, beliefs, uncertainties, watched changes, or reflection references — confirmed by both the module docstring and the actual call graph.
- **What it can propose**: The full pipeline per source record: fetch → build text → check processed-source ledger → generate candidates deterministically (self-subject + literal name-mention scan, `entity_type='person'` only, never via Gemini or pronoun resolution) → one Gemini evaluation per candidate → strict deterministic validation (subject-name match, taxonomy membership, non-empty fact, confidence in [0.6, 1.0], evidence_quote must be an exact substring of source text) → hybrid duplicate suppression (exact fingerprint first; only if that finds nothing, a narrow Gemini semantic-equivalence check, conservatively biased so any parse failure = "not a duplicate") → write to `hearth_furniture_proposals`.
- **What it can never do**: Write `hearth_entity_furniture` directly (only `hearth_furniture_proposals.approve_furniture_proposal()`, human-triggered, does that). Create beliefs, uncertainties, watched changes, or reflection references. Use Gemini for candidate selection or duplicate fingerprinting — Gemini is scoped to (a) single-Building fact extraction and (b) semantic-equivalence judgments only. Resolve pronouns into candidates. Backfill history before `GO_LIVE_AT`. Inspect "Live Discussions" (explicitly out of scope, storage location undefined) or private creator DMs / private creator-to-creator metadata — this is directly tested (`test_fact_extractor.py:274-285` asserts the exact expected set of 8 source types, "no DMs, no Live Discussions") and is the one piece of code in this codebase that explicitly cross-references and self-audits against `HEARTH_SENSORY_POLICY.md` in both code and tests.
- **Rooms touched**: Furniture only (indirectly, via human-approved proposals).
- **Dependencies**: `hearth_entity_resolution`, `hearth_furniture` (read-only, for dedup), `hearth_furniture_proposals` (write), `hearth_memory`, `hearth_furniture_taxonomy.FURNITURE_CATEGORIES`, `hearth_gemini_config.GEMINI_MODEL_NAME`. Soft dependency on `google.genai` — the whole run is skipped (not errored) if `GEMINI_API_KEY` is unset or the package is missing.
- **Consumers**: `pathway-portal/backend/app/commands.py` — CLI command `run-furniture-fact-extractor`. `pathway-portal/backend/app/hearth_scheduler.py` — daily APScheduler job at 5:30 AM CT, gated on `gemini_enabled`, deliberately scheduled before the 6:00 AM Calendar Watcher and 7:00 AM Daily Brief so proposals are ready for morning review. `hearth_reader.py` — the furniture-proposal wrapper functions (see `HEARTH_MIND_03`).

**Notable gaps, both self-documented as intentional**: `_is_hearth_authored()` (:300-313) is a permanent stub always returning `False` — the extractor has no way today to detect and skip its own prior output, because no approved source table currently has a Hearth-authorship marker; this is a real self-ingestion risk if that ever changes silently. No test coverage exists for `run_batch()` end-to-end — the SQL in `SOURCE_CONFIGS` is untested against a real or mocked Pathway DB, so a Pathway schema drift (e.g. a renamed column) would only surface at 5:30 AM production run time, caught only by a per-record try/except that logs and continues.

## Training Comment Classifier (`hearth_comment_classifier.py`)

- **Purpose**: Classify the *type* of a training comment (question, help_request, feedback_request, discussion, observation, celebration, appreciation, other) at write time, so downstream logic can decide whether a comment is actionable without re-reading raw text or making its own LLM call. Explicitly scoped: "You are NOT deciding whether a manager should respond... NOT answering... NOT summarizing" (:49-51).
- **What it knows**: A fixed 8-category taxonomy with prompt guidance per category; a safe default `("other", 0.0)` for any failure mode.
- **What it can read**: Only the comment-text string passed as an argument — no DB access of its own.
- **What it can write**: Nothing directly — a pure function, `classify_training_comment(text) -> (category, confidence)`. The caller persists the result.
- **What it can never do**: Raise into the caller — every failure mode (missing API key, missing package, Gemini failure, unparseable JSON, invalid category, non-numeric confidence) falls back to the safe default.
- **Dependencies**: `hearth_gemini_config.GEMINI_MODEL_NAME`.
- **Consumers**: `pathway-portal/backend/app/routes/main.py:680` — called synchronously in the training-comment POST handler ("flush → classify → commit") before setting `comment.comment_type`/`comment.comment_type_confidence`. `backfill_training_comment_classification.py`. `morning_briefing.py` — imports `ACTIONABLE_COMMENT_TYPES` and reads the *already-stored* classification; "Pulse reads the stored classification; it never calls Gemini" (:5).

**Historical note**: This is the exact file named in `hearth_gemini_config.py`'s own docstring as the one that "went unnoticed" during a prior manual model-name edit, causing it to silently run against a deprecated model. It is now correctly centralized. See `HEARTH_MIND_11_INFRASTRUCTURE.md`.

## Training Comment Classification Backfill (`backfill_training_comment_classification.py`)

- **Purpose**: One-time, two-part maintenance script. Part A retroactively classifies legacy `training_comments` rows written before the classifier existed. Part B resolves stale `training_comment_waiting` Hearth episodes that turn out to be false positives once their underlying comment is classified as non-actionable.
- **What it can read**: Pathway's `training_comments` (id, content, comment_type) via a **read-write** connection (not read-only — a deliberate, narrow exception to the general Hearth-is-read-only-toward-Pathway posture, since this script's whole job is to write a classification back). `hearth_episodes` (open `training_comment_waiting` episodes).
- **What it can write**: Pathway's `training_comments.comment_type`/`.comment_type_confidence` — the **only capability in this inventory that writes back into the Pathway Portal database itself**, guarded by `AND comment_type IS NULL` so it never overwrites an existing classification. `hearth_episodes`, via `hearth_memory.refresh_episode()`/`resolve_episode()` — never deletes.
- **What it can never do**: Touch rows that already have a `comment_type`. Re-open or delete an episode. Touch episodes whose comment is still classified as actionable.
- **Rooms touched**: Episodes.
- **Consumers**: None — standalone, manually run, not wired into `commands.py`, the scheduler, or any Flask route.
